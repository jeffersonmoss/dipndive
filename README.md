# dipdive

PoC 1 of the Dip & Dive companion: acquisition (plan 3.3), isolated model calls (3.4) and prompts (3.5) as an importable Python module, plus a CLI. Plan: `CODEX PROJECTS/DIP_DIVE/PLAN.md` (see POINTER.md there).

## Use

    .venv/bin/python -m dipdive <url> <claude-dip|claude-dive|codex-dip|codex-dive|source>

Prints the summary, or `ERROR <code>: <message>` on stderr with exit status 1. The later HTTP server imports `dipdive.cli.run_job(url, mode)`, `dipdive.acquire.acquire(url)` and `dipdive.models.call_model(...)`.

## Server (plan 3.2, Stage A)

    .venv/bin/python -m dipdive.server [port]     # default 8765, binds 127.0.0.1 only

Files: `dipdive/service.py` (job store, source cache, workers, health), `dipdive/server.py` (HTTP, auth). State lives in `~/Library/Application Support/DipDive/` (override with `DIPDIVE_SUPPORT`): `jobs/`, `sources/`, `results/`, `logs/`, `state.json` (clear generation), `token` (0600, created on first start, never printed). Requests need `Authorization: Bearer <token>`; requests with a web-page `Origin` or a non-loopback, non-`*.ts.net` Host are refused; there is no CORS.

Endpoints: `POST /jobs {url, mode, requestId, force?, question?, history?, summary?, clearGeneration?}` (202 new, 200 existing, 409 `request_id_conflict` or `stale_clear_generation`, 429 `queue_full`), `GET /jobs/{id}` (a missing job is 404 `no_such_job` with the current `clear_generation`), `GET /source?job=<id>` (cache only, never fetches), `GET /history` (the history log, see below), `POST /history/{job_id}/remove` and `/restore` (the panel's save box, see below), `POST /clear`, `GET /health`. `clearGeneration` (optional integer) is the clear generation the client last saw (every answer and `/health` carry the current one). One older than the companion's own is refused with 409 `stale_clear_generation` (the body carries the current `clear_generation`) before anything else happens: no job, no fetch, no model call, nothing stored, and the `requestId` is not remembered. It means another machine pressed Clear history after the client's summary and question thread were built, so they no longer belong to the companion's history. A client that has seen no generation yet leaves the field out; one that is ahead of the companion (the state file was lost) is served, and the lower generation in the answer tells it so. A value that is not a non-negative integer is a 400. Dedupe key is sha256 of normalized source id, mode, model id and prompt version (plus a hash of the question, history and summary for the ask modes); the result cache additionally includes a hash of the source text.

Ask modes (`claude-ask`, `codex-ask`, `dipdive/ask.py`): `question` (required, at most 2000 characters, whitespace collapsed), optional `history` (`[{"q","a"}, ...]`, oldest first) and optional `summary` (the Dip or Dive text the panel is showing; the first 4000 characters are kept). Every limit and the emptiness check apply to the normalized text (NFKC, invisible and default-ignorable characters removed, lone surrogates replaced by U+FFFD), which is what reaches the model, so a character that NFKC expands cannot get past a limit and a question of only zero-width characters is refused; text the JSON carries that cannot be UTF-8 encoded is repaired, never a 500. The companion keeps the newest 6 turns, clips one earlier question to 500 and one earlier answer to 3000 characters, then drops the oldest turns until at most 8000 characters remain; the cache key hashes the question, that capped history and the summary, so what the panel trimmed never changes the key. Same isolated model call as Dip and Dive (same Claude and Codex flags, 45 s limit, Codex at low effort), same source cache and coalescing, same `requestId` idempotency (a reused `requestId` with another question is 409). The question, the summary, every earlier turn and the source are neutralized against the `<source>`, `<summary>`, `<history>`, `<turn>`, `<asked>`, `<answered>` and `<question>` delimiters (look-alikes, entity and percent forms, and every default-ignorable character are handled); each earlier turn sits in its own `<turn>` block, so an answer that quotes `Q: ...` lines cannot pass for a user question; the source, the summary and the earlier answers stay untrusted data and only `<question>` and `<asked>` are the user's own words. The prompt asks for at most about five sentences, a plain "the source does not cover that" when it does not, no invention, and one short sentence naming the possibilities when a reference such as "the second one" cannot be resolved. `question`, `history` or `summary` on a non-ask mode is a 400. `PROMPT_VERSION` is `p4` (p3 added the ask prompt; every bump invalidates cached Dip and Dive results once).

History log (`dipdive/historylog.py`): every time a Dip or Dive job (`claude-dip`, `claude-dive`, `codex-dip`, `codex-dive`) finishes successfully, one Markdown entry is appended to a durable log. Default `~/Public/Dip'n'Dive Log.md` (the iMac's shared Public folder, readable from other machines); set `DIPDIVE_LOG_PATH` to move it. The file is created with a one-line heading if missing. Newest entries are at the bottom; each is a `## <title>` heading, an optional `Channel: <name>` line (YouTube `channel`, else `uploader`, from the yt-dlp metadata kept with the cached source as `meta.channel`; for articles the site name trafilatura finds; omitted when unknown, as for sources cached before this field existed; newlines collapsed like the title), a line `YYYY-MM-DD HH:MM | Claude Dip | [url](<url>)` (local time, mode label, link), directly under it the writer's marker as an HTML comment, `<!-- dipdive-job: <32 hex> seq=<n> -->` (the id of the job that made the entry and an ever-increasing sequence number, kept in the sidecar lock file and never below the clock in nanoseconds; invisible when the Markdown is rendered; entries written before it existed have no marker, or a marker without `seq`), the summary exactly as shown, a blank line and `---`. The entry is written before the job reads as done, so a panel that sees "done" also sees whether it has an entry. Not logged: asks, `source` jobs, errors, and results served from the result cache or by deduplication (a job is logged only when a model call just produced its text; a forced re-run is a new result and is logged, and so is the same video summarized again after Clear history, because the result cache is gone by then). A job that is cleared while it runs is not logged. Every writer (appends, the remove and restore below, and Clear history around its own work) first takes the log's write lock: an in-process lock, then an advisory `flock` on a stable sidecar file next to the log, `.Dip'n'Dive Log.md.lock`, which is never replaced, so a writer in another process can never be left waiting on a log file that a rewrite has since replaced. Appends go out as one write, so two jobs finishing together leave two intact entries. The only edits to the summary are a line made only of hyphens (a rule) gaining a leading backslash so it cannot pass for the separator, and a code fence left open being closed. A log failure never fails the job: the error is written to the job log (`logs/`, key `history_log_error`). **Clear history (`POST /clear`) does not touch this log**; it is deliberately outside the support folder, and deleting it is a manual act.

Taking one entry out and putting it back (`POST /history/{job_id}/remove` and `POST /history/{job_id}/restore`, body `{}`, same bearer token and host and origin rules): the panel's "Save this Dip to history" box. `job_id` is a job id; for a job whose result came from the result cache it means the entry of the job that made that result (the result file keeps that id), and an id with no job record (an older entry) is taken as the entry's own id. Remove cuts the entry out of the log and keeps its exact text, the ids of the entries before and after it and its date, in `history-removed/<id>.json` in the support folder. Restore puts the text back by its sequence number, right before the first later entry (or at the bottom), next to its old predecessor when that is still the entry before that spot; for an entry without a sequence number it goes after the entry that was before it, else before the one that was after it, else among the others by its date, stepping past older or before newer neighbours so the dates stay in order; remove then restore with nothing in between gives back the identical file (CRLF logs too). Each is one transaction under the log's write lock: remove writes the kept copy, rewrites the log, and deletes the copy again if the rewrite fails; restore rewrites the log and deletes the copy only afterwards. The rewrite reads the whole log, edits it and replaces the file atomically (temp file in the same folder, fsync, rename, the old file mode kept). Both are idempotent and answer `200 {job_id, saved, clear_generation}` (`saved` false after remove, true after restore); restoring an entry that is already in the log drops a stale kept copy. The body may carry `clearGeneration`; one older than the companion's is refused with `409 stale_clear_generation` and changes nothing, and Clear history takes the log's write lock first, so a remove or restore is never half done around a clear (a copy kept before a clear is deleted with it). An entry whose text runs into a neighbour's (a hand edit deleted the neighbour's heading, so the neighbour's marker sits inside it) is refused with `409 entry_ambiguous` and nothing changes. An id in neither the log nor the removed store is `404 no_such_entry`; a job with no log entry (asks, Temp chat, errors, a log write that failed, a cached result from before entries had ids) is `404 not_logged`; a log that cannot be read is `503 log_unreadable`, one that cannot be written `503 log_unwritable`. Every `GET /jobs/{id}` carries `history_saved`, read from the log itself (the job ids in the log are cached on the file's identity, size and change time): true while the entry is in the log, false while it is not but is kept as removed, null when it is in neither (or the summary never had one). `POST /clear` deletes `history-removed/` with the rest of the support folder's history (the log itself stays). `GET /health` carries `log_path` and `log_writable` (checked live, touches nothing).

Reading the log (`GET /history?limit=20&before=<position>`, same bearer token and host and origin rules as every other endpoint): the entries parsed back out of the file at `DIPDIVE_LOG_PATH`, newest first, one page per request. Each entry is `{title, channel, date, time, mode, mode_label, url, summary, index}` (`date` and `time` are the local `YYYY-MM-DD` and `HH:MM` written in the log, `mode` is the id such as `claude-dip`, `mode_label` the text in the log, `summary` is the Markdown as written with the rule-line escape undone, `index` the entry's position in the file, 0 for the oldest). The answer is `{entries, total, limit, next_before, revision}`; each entry also has `job_id` ("" for entries written before ids existed). `limit` is 1 to 100 (default 20). `before` is a position: only entries below it are returned, and omitted it means the newest. `next_before` is the `before` for the next page and `null` on the last one. It is a cursor and not an offset because new entries are appended at the bottom: a reader paging down while a job finishes neither repeats nor skips an entry. Removing or restoring an entry does move positions, so it changes `revision` (a counter kept in the sidecar lock file; appends leave it alone). A page and its revision are read together under the log's write lock, so no change can fall between them. A request for a later page that passes `revision=<n>` from its first page gets `409 history_changed` (with the current `revision`) when it no longer matches, and the panel then starts again from the newest entry with one line saying why; without `revision` the old behaviour is unchanged. A missing log is `200` with no entries; a log that exists but cannot be read (permissions, a directory in its place) is `503 log_unreadable`; a bad `limit` or `before` is `400`. Parsing is tolerant and goes by marks a summary cannot forge, not by separator formatting: the text is split on "\n" only (a CR or U+2028 stays inside its line). An entry starts at a `## ` heading outside a code fence, followed by the stamp line and the writer's marker; an entry with no marker (written before markers existed) starts only right after a separator line, the file heading or the start of the file. The writer escapes every summary line that starts like a marker (a leading backslash, removed again when read) and every hyphen-only rule line, and closes any code fence a summary leaves open, so a summary that quotes a heading, a stamp line and even a marker stays one entry. An entry ends at its first separator line (`---`, optionally followed by spaces or tabs) or at the next entry, whichever comes first. Text that is not part of an entry (hand edits, a heading with no stamp line) is skipped, never an error, and an entry whose separator was edited into `***` or deleted is still read on its own. A log over 32 MB is read from its tail only.

iMac deployment (written, not loaded anywhere): `deploy/install-imac.sh [--dry-run] [--port N]` renders `deploy/com.jeffersonmoss.dipdive.plist.template` (RunAtLoad, KeepAlive, ThrottleInterval 10, explicit PATH, `DIPDIVE_DENO`), bootstraps it into the GUI session, and runs `tailscale serve --bg --https=443`. ### Waterline (the panel's design)

The panel is a cross-section of the icon: dry air on top (the duck, the link field, the title), the icon's waterline, then the water, where the five mode buttons hang from the surface to their own depth and the answer is read, and the docked question bar at the bottom is the deep water. The waterline is traced from `icons/source-1024-inverted.png`: the line's centre was sampled across the icon, the stretch the duck's body interrupts was bridged by interpolation, and the result was smoothed and scaled to 360 units wide with the icon's proportions, about 5 units from crest to trough. It is one SVG path (`--wave` in `panel.css`, the same in `pages.css`), drawn stretched to the panel width and 9 px tall, for the surface line, the water under it, the mask that cuts the mode buttons off at the surface (each button's top follows the line, also a pressed one, which sinks 6 px), and the edge of the question bar. Day is the icon itself: white air, pale water, an ink line. Night (`prefers-color-scheme: dark`) is night water: an ink-blue sky, deep navy water under a moonlit line, the question bar nearly black with a faint moonlit edge; the buttons stay in their orange and blue families and the Dip squares stay pale with dark text. The Settings and microphone pages use the same air, line and water in both modes.

### Footer: save box, History, Settings

The footer row holds, left to right, a "Save this Dip to history" (or "Save this Dive to history") checkbox, the History button and a gear button (accessible name "Settings", 44 px) that opens the Settings page. The checkbox matches the mode of the summary on screen and is shown only when a Dip or Dive summary is shown that has an entry in the history log: never in Temp chat, never without a summary. It starts ticked, because the companion logs every summary when it finishes. Unticking it removes that summary's entry from the log (`POST /history/{job_id}/remove`); ticking it again puts the entry back where it was (`/restore`). The box follows the click at once and goes back, with one line in the status, when the companion refuses. When the answer is lost (the companion may have made the change), the panel says the outcome is not known yet and asks the companion (`GET /jobs/{id}`, `history_saved`); if that fails too, the box is shown as indeterminate with a line saying so, and the next click retries. An answer that arrives after another summary replaced this one is dropped. Each change, including one learned that way after a lost answer, is announced to the panels of the other windows (storage key `savedChange`), which ask the companion again, and every panel asks again when it gets the focus, so two panels showing the same summary never disagree for long. An answer to such a question that was asked before a later click in this panel is dropped, and one that carries a newer clear generation (Clear history on another machine) resets the panel like a cleared one: summary, box and thread go, and it says so. Reopening the panel shows the state the companion reports. The request carries the panel's clear generation; a refusal as stale resets the panel like any other stale refusal.

Clear history is no longer in the panel. It is on the Settings page, under History, behind a confirmation ("Clear history now?" with "Yes, clear history" and Cancel; Escape cancels). Confirming does what the panel button used to: `POST /clear`, every per-window slot dropped from storage, and the new generation written as `clearGen`, so every open panel forgets its summary and question thread ("History was cleared in another window or on the Options page."). The history log file is kept.

### History link

History replaces the summary and the question box with a scrolling list of the history log (see "Reading the log" above): a sticky bar with a Back button, then one card per entry, newest first, 20 at a time. A card has the title (a link that opens the page in a new tab, only when the URL is http or https), the channel when there is one, the date, time and mode, and the summary through the same safe Markdown renderer as the panel (HTML escaped, images never rendered). A Show older button at the bottom adds the next page; Back returns to the summary and question box exactly as they were. Opening History always starts again from the newest entry. A failed page shows one plain line (cannot reach the companion, token refused, log unreadable) and the button becomes Try again; what is already on screen stays. The microphone is stopped when History opens. Everything is a click. Real-browser check: `node tests/chrome/panel-history.mjs` (seeds the harness log with `DIPDIVE_HARNESS_HISTORY=45`; also unticks and reticks the save box against the real companion log and checks it is hidden in Temp chat).

### The five buttons

Five large square buttons, left to right: Claude Dive, Claude Dip, Temp chat, Codex Dip, Codex Dive. The shallowest immersion (Temp chat) is in the center and the water gets deeper toward both edges. Colors: Claude Dip pale orange, Claude Dive the Claude orange `#D97757`, Codex Dip pale blue, Codex Dive full blue, Temp chat white or neutral; the Dip squares stay pale in dark mode too. The pressed button looks physically pressed in (inset, shifted down, darker edge); there are no radio buttons. The buttons are created from one ordered list (`MODES` in `lib/modes.js`) and nothing reorders them, so the Tab order is the same left to right.

### Question box and microphone (mouse only)

Below the result the panel has a box ("Ask a question"), a mic button and an Ask button. These controls are docked at the bottom of the panel: everything else (summary, thread, status) scrolls above them, and every message line (listening, errors, Enable microphone) grows upward from them, so nothing arriving while the person talks can move the mic button between the click that starts a recording and the click that stops it. Typing and Enter, or the Ask button, send the question. The mic is click to start, click again to stop: the button turns red and says Stop, the words appear in the box as they are recognized, and the second click sends the text automatically. Everything is reachable with the mouse. The previous questions and answers in this panel for this source (newest 6 turns, 8000 characters) and the Dip or Dive text on screen (first 4000 characters) go along with each question, so follow-ups work ("and why?", "tell me more about the second one"). Each earlier turn is sent in its own `<turn>` block and the summary in `<summary>`; they and the source are data, never instructions. The thread is forgotten when the source changes (another link, typed or right-clicked; the same video written another way keeps it), on Clear history (on the Settings page: every panel learns of it through a `clearGen` storage key and also from the generation number in the companion's answers). Clear history on another machine cannot reach this browser's storage, so every `POST /jobs` (summary, Temp chat and question) carries the clear generation the panel knows (`clearGeneration`, left out until the panel has heard one). If the companion answers 409 `stale_clear_generation`, the panel forgets its thread and summary, adopts the companion's generation, shows "History was cleared on another machine." (in the page for a button press, next to the question box for a question, which goes back into the box), and sends nothing again by itself: the next press or Ask is the person's own and carries the new generation. A link from a right-click or Go that was refused is dropped from storage so reopening the panel does not submit it later, and when the panel closes. The provider follows the pressed button: Claude Dive and Dip ask Claude, Codex Dip and Dive ask Codex, Temp chat asks Codex unless `/health` says Codex is unavailable (then Claude).

Speech recognition is Chrome's built-in `webkitSpeechRecognition` (English, interim results, continuous mode), running in the side panel page itself. Chrome ends a continuous session by itself after about 15 seconds of silence (8 seconds if nothing is said at the start); when that happens, or when the panel is hidden, the recognized words are kept in the box and are not sent, with one line saying so, so a long pause never sends half a question. Words typed in the box before the mic is clicked stay, and the spoken words are added after them; Chrome sends the audio to Google's speech service. A side panel cannot show Chrome's microphone prompt, so the panel checks `navigator.permissions` for the microphone and, when it is not granted, shows an Enable microphone button. That opens `mic.html` in a normal tab, which calls `getUserMedia({audio:true})`, stops the tracks and tells the user to go back to the panel (the button to click in Chrome's prompt is "Allow while visiting the site", not "Allow this time"). If the computer itself blocks the microphone for Chrome (macOS Privacy and Security, Windows privacy switches), both the tab and the panel say so and name the setting instead of looping through the prompt. No offscreen document and no extra manifest permission are needed (evidence in RESULTS section 13). Real-Chrome checks (throwaway Chrome profile, never the real one, everything removed on exit): `node tests/chrome/speech-probe.mjs [--headed --side-panel] [--no-grant]` for the recognizer, `node tests/chrome/panel-e2e.mjs` for the real panel, `mic.html` and the permission flow against the dev harness.
