# dipdive

PoC 1 of the Dip & Dive companion: acquisition (plan 3.3), isolated model calls (3.4) and prompts (3.5) as an importable Python module, plus a CLI. Plan: `CODEX PROJECTS/DIP_DIVE/PLAN.md` (see POINTER.md there).

## Use

    .venv/bin/python -m dipdive <url> <claude-dip|claude-dive|codex-dip|codex-dive|source>

Prints the summary, or `ERROR <code>: <message>` on stderr with exit status 1. The later HTTP server imports `dipdive.cli.run_job(url, mode)`, `dipdive.acquire.acquire(url)` and `dipdive.models.call_model(...)`.

## Server (plan 3.2, Stage A)

    .venv/bin/python -m dipdive.server [port]     # default 8765, binds 127.0.0.1 only

Files: `dipdive/service.py` (job store, source cache, workers, health), `dipdive/server.py` (HTTP, auth). State lives in `~/Library/Application Support/DipDive/` (override with `DIPDIVE_SUPPORT`): `jobs/`, `sources/`, `results/`, `logs/`, `state.json` (clear generation), `token` (0600, created on first start, never printed). Requests need `Authorization: Bearer <token>`; requests with a web-page `Origin` or a non-loopback, non-`*.ts.net` Host are refused; there is no CORS.

Endpoints: `POST /jobs {url, mode, requestId, force?, question?, history?, summary?, clearGeneration?}` (202 new, 200 existing, 409 `request_id_conflict` or `stale_clear_generation`, 429 `queue_full`), `GET /jobs/{id}` (a missing job is 404 `no_such_job` with the current `clear_generation`), `GET /source?job=<id>` (cache only, never fetches), `GET /history` (the history log, see below), `POST /history/{job_id}/remove` and `/restore` (the panel's save box, see below), `POST /clear`, `GET /health`. `clearGeneration` (optional integer) is the clear generation the client last saw (every answer and `/health` carry the current one). One older than the companion's own is refused with 409 `stale_clear_generation` (the body carries the current `clear_generation`) before anything else happens: no job, no fetch, no model call, nothing stored, and the `requestId` is not remembered. It means another machine pressed Clear history after the client's summary and question thread were built, so they no longer belong to the companion's history. A client that has seen no generation yet leaves the field out; one that is ahead of the companion (the state file was lost) is served, and the lower generation in the answer tells it so. A value that is not a non-negative integer is a 400. Dedupe key is sha256 of normalized source id, mode, model id and prompt version (plus a hash of the question, history and summary for the ask modes); the result cache additionally includes a hash of the source text.

Ask modes (`claude-ask`, `codex-ask`, `dipdive/ask.py`): `question` (required, at most 2000 characters, whitespace collapsed), optional `history` (`[{"q","a"}, ...]`, oldest first) and optional `summary` (the Dip or Dive text the panel is showing; the first 4000 characters are kept). Every limit and the emptiness check apply to the normalized text (NFKC, invisible and default-ignorable characters removed, lone surrogates replaced by U+FFFD), which is what reaches the model, so a character that NFKC expands cannot get past a limit and a question of only zero-width characters is refused; text the JSON carries that cannot be UTF-8 encoded is repaired, never a 500. The companion keeps the newest 6 turns, clips one earlier question to 500 and one earlier answer to 3000 characters, then drops the oldest turns until at most 8000 characters remain; the cache key hashes the question, that capped history and the summary, so what the panel trimmed never changes the key. Same isolated model call as Dip and Dive (same Claude and Codex flags, 45 s limit, Codex at low effort), same source cache and coalescing, same `requestId` idempotency (a reused `requestId` with another question is 409). The question, the summary, every earlier turn and the source are neutralized against the `<source>`, `<summary>`, `<history>`, `<turn>`, `<asked>`, `<answered>` and `<question>` delimiters (look-alikes, entity and percent forms, and every default-ignorable character are handled); each earlier turn sits in its own `<turn>` block, so an answer that quotes `Q: ...` lines cannot pass for a user question; the source, the summary and the earlier answers stay untrusted data and only `<question>` and `<asked>` are the user's own words. The prompt asks for at most about five sentences, a plain "the source does not cover that" when it does not, no invention, and one short sentence naming the possibilities when a reference such as "the second one" cannot be resolved. `question`, `history` or `summary` on a non-ask mode is a 400. `PROMPT_VERSION` is `p4` (p3 added the ask prompt; every bump invalidates cached Dip and Dive results once).

History log (`dipdive/historylog.py`): every time a Dip or Dive job (`claude-dip`, `claude-dive`, `codex-dip`, `codex-dive`) finishes successfully, one Markdown entry is appended to a durable log. Default `~/Public/Dip'n'Dive Log.md` (the iMac's shared Public folder, readable from other machines); set `DIPDIVE_LOG_PATH` to move it. The file is created with a one-line heading if missing. Newest entries are at the bottom; each is a `## <title>` heading, an optional `Channel: <name>` line (YouTube `channel`, else `uploader`, from the yt-dlp metadata kept with the cached source as `meta.channel`; for articles the site name trafilatura finds; omitted when unknown, as for sources cached before this field existed; newlines collapsed like the title), a line `YYYY-MM-DD HH:MM | Claude Dip | [url](<url>)` (local time, mode label, link), directly under it the writer's marker as an HTML comment, `<!-- dipdive-job: <32 hex> seq=<n> -->` (the id of the job that made the entry and an ever-increasing sequence number, kept in the sidecar lock file and never below the clock in nanoseconds; invisible when the Markdown is rendered; entries written before it existed have no marker, or a marker without `seq`), the summary exactly as shown, a blank line and `---`. The entry is written before the job reads as done, so a panel that sees "done" also sees whether it has an entry. Not logged: asks, `source` jobs, errors, and results served from the result cache or by deduplication (a job is logged only when a model call just produced its text; a forced re-run is a new result and is logged, and so is the same video summarized again after Clear history, because the result cache is gone by then). A job that is cleared while it runs is not logged. Every writer (appends, the remove and restore below, and Clear history around its own work) first takes the log's write lock: an in-process lock, then an advisory `flock` on a stable sidecar file next to the log, `.Dip'n'Dive Log.md.lock`, which is never replaced, so a writer in another process can never be left waiting on a log file that a rewrite has since replaced. The lock fails closed: when the sidecar cannot be opened or locked (read-only, missing folder, no flock), nothing is written. An append is skipped and the error goes to the job log (`history_log_error`, the job itself still succeeds, with no entry); remove and restore answer `503 log_locked`; `GET /history` answers `503 log_locked` rather than a page whose revision cannot be trusted (a log that does not exist yet still pages as empty). Only Clear history, which never writes the log, goes ahead without it. On every start the companion gives each entry that has no sequence number one (in file order, from its date where that fits, under the lock, once), adding a marker with a fresh id to an entry that had none, so restore can always place entries by number. Appends go out as one write, so two jobs finishing together leave two intact entries. The only edits to the summary are a line made only of hyphens (a rule) gaining a leading backslash so it cannot pass for the separator, and a code fence left open being closed. A log failure never fails the job: the error is written to the job log (`logs/`, key `history_log_error`). **Clear history (`POST /clear`) does not touch this log**; it is deliberately outside the support folder, and deleting it is a manual act.

Taking one entry out and putting it back (`POST /history/{job_id}/remove` and `POST /history/{job_id}/restore`, body `{}`, same bearer token and host and origin rules): the panel's "Save this Dip to history" box. `job_id` is a job id; for a job whose result came from the result cache it means the entry of the job that made that result (the result file keeps that id), and an id with no job record (an older entry) is taken as the entry's own id. Remove cuts the entry out of the log and keeps its exact text, the ids of the entries before and after it and its date, in `history-removed/<id>.json` in the support folder. Restore puts the text back by its sequence number, right before the first later entry (or at the bottom), next to its old predecessor when that is still the entry before that spot; for an entry without a sequence number it goes after the entry that was before it, else before the one that was after it, else among the others by its date, stepping past older or before newer neighbours so the dates stay in order; remove then restore with nothing in between gives back the identical file (CRLF logs too). Each is one transaction under the log's write lock: remove writes the kept copy, rewrites the log, and deletes the copy again if the rewrite fails; restore rewrites the log and deletes the copy only afterwards. The rewrite reads the whole log, edits it and replaces the file atomically (temp file in the same folder, fsync, rename, the old file mode kept). Both are idempotent and answer `200 {job_id, saved, clear_generation, history_rev}` (`saved` false after remove, true after restore); restoring an entry that is already in the log drops a stale kept copy, and a restore whose entry is back but whose kept copy cannot be deleted still answers 200 (the copy is dropped later; the state is read from the log). The body may carry `clearGeneration`; one older than the companion's is refused with `409 stale_clear_generation` and changes nothing, and Clear history takes the log's write lock first, so a remove or restore is never half done around a clear (a copy kept before a clear is deleted with it). An entry whose text runs into a neighbour's (a hand edit deleted the neighbour's heading, so the neighbour's marker sits inside it) is refused with `409 entry_ambiguous` and nothing changes. An id in neither the log nor the removed store is `404 no_such_entry`; a job with no log entry (asks, Temp chat, errors, a log write that failed, a cached result from before entries had ids) is `404 not_logged`; a log that cannot be read is `503 log_unreadable`, one that cannot be written `503 log_unwritable`. Every `GET /jobs/{id}` carries `history_rev` (the log's revision, read before the state, so the state is never older than its label) and `history_saved`, read from the log itself (the job ids in the log are cached on the file's identity, size and change time): true while the entry is in the log, false while it is not but is kept as removed, null when it is in neither (or the summary never had one). `POST /clear` deletes `history-removed/` with the rest of the support folder's history (the log itself stays). `GET /health` carries `log_path` and `log_writable` (checked live, touches nothing).

Reading the log (`GET /history?limit=20&before=<position>`, same bearer token and host and origin rules as every other endpoint): the entries parsed back out of the file at `DIPDIVE_LOG_PATH`, newest first, one page per request. Each entry is `{title, channel, date, time, mode, mode_label, url, summary, index}` (`date` and `time` are the local `YYYY-MM-DD` and `HH:MM` written in the log, `mode` is the id such as `claude-dip`, `mode_label` the text in the log, `summary` is the Markdown as written with the rule-line escape undone, `index` the entry's position in the file, 0 for the oldest). The answer is `{entries, total, limit, next_before, revision}`; each entry also has `job_id` ("" for entries written before ids existed). `limit` is 1 to 100 (default 20). `before` is a position: only entries below it are returned, and omitted it means the newest. `next_before` is the `before` for the next page and `null` on the last one. It is a cursor and not an offset because new entries are appended at the bottom: a reader paging down while a job finishes neither repeats nor skips an entry. Removing or restoring an entry does move positions, so it changes `revision` (a counter kept in the sidecar lock file; appends leave it alone). A page and its revision are read together under the log's write lock, so no change can fall between them. A request for a later page that passes `revision=<n>` from its first page gets `409 history_changed` (with the current `revision`) when it no longer matches, and the panel then starts again from the newest entry with one line saying why; without `revision` the old behaviour is unchanged. A missing log is `200` with no entries; a log that exists but cannot be read (permissions, a directory in its place) is `503 log_unreadable`; a bad `limit` or `before` is `400`. Parsing is tolerant and goes by marks a summary cannot forge, not by separator formatting: the text is split on "\n" only (a CR or U+2028 stays inside its line). An entry starts at a `## ` heading outside a code fence, followed by the stamp line and the writer's marker; an entry with no marker (written before markers existed and not yet migrated) starts only right after a separator line, the file heading on the very first line, or the start of the file. The writer escapes every summary line that starts like a marker (a leading backslash, removed again when read) and every hyphen-only rule line, and closes any code fence a summary leaves open, so a summary that quotes a heading, a stamp line and even a marker stays one entry. An entry ends at its first separator line (`---`, optionally followed by spaces or tabs) or at the next entry, whichever comes first. Text that is not part of an entry (hand edits, a heading with no stamp line) is skipped, never an error, and an entry whose separator was edited into `***` or deleted is still read on its own. A log over 32 MB is read from its tail only.

### History tab

The History button opens `history.html` in a tab of its own, or brings the one already open to the front (found with `chrome.runtime.getContexts`, which needs no extra permission). The panel does not do this itself: it sends the service worker a runtime message, and the worker runs one lookup-or-create at a time, shared by every panel and window (a click that arrives while one is running joins it, and the tab it opened is remembered until `getContexts` lists it), so quick clicks cannot open two tabs. A tab that is brought forward is sent a refresh message, and it also reloads whenever it becomes visible again: the page rereads the companion URL and token from storage and refetches every page, keeping the search typed in the box (and the entries already shown if the reload fails, beside the error line). The page loads the whole history log from the companion: it follows `GET /history` page by page (100 at a time) to the end, every later page carrying the revision of the first, and starts again from the newest when the companion answers `409 history_changed` (an entry was removed or restored meanwhile), giving up with a plain line after five restarts. Entries are shown newest first in a reading column: the title (a link to the page, only for http and https), the channel, the date and time with the mode, and the summary through the panel's safe Markdown renderer (HTML escaped, images never rendered). A search box at the top filters live: every word typed must appear (any case, any order) in the title, the channel or the summary, and a line says how many entries match. Since everything is loaded, the browser's own Find (Cmd or Ctrl+F) works too. Light and dark follow the system. A failure (no settings, token refused, log unreadable or locked, companion unreachable) is one plain line. Real-browser check: `node tests/chrome/panel-history.mjs` (seeds 145 entries, more than one page; also unticks and reticks the save box against the real companion log and checks the bottom row, the status line and the mode logos); `node tests/chrome/panel-e2e.mjs` checks in the real extension that History opens the tab and a second click reuses it.

### Save box, History, Settings

The status line under the summary holds, after the status text, a "Save this Dip to history" (or "Save this Dive to history") checkbox and a small gear button (accessible name "Settings") that opens the Settings page; History is the first button of the docked bottom row and opens the History tab. The checkbox matches the mode of the summary on screen and is shown only when a Dip or Dive summary is shown that has an entry in the history log: never without a summary. It starts ticked, because the companion logs every summary when it finishes. Unticking it removes that summary's entry from the log (`POST /history/{job_id}/remove`); ticking it again puts the entry back where it was (`/restore`). The box follows the click at once and goes back, with one line in the status, when the companion refuses. When the answer is lost (the companion may have made the change), the panel says the outcome is not known yet and asks the companion (`GET /jobs/{id}`, `history_saved`); if that fails too, the box is shown as indeterminate with a line saying so, and the next click retries. An answer that arrives after another summary replaced this one is dropped. Each change, including one learned that way after a lost answer, is announced to the panels of the other windows (storage key `savedChange`), which ask the companion again, and every panel asks again when it gets the focus, so two panels showing the same summary never disagree for long. Every answer about the box carries the log's revision, and a panel applies only answers at least as new as the newest it has seen, whether they come from its own click, a GET on focus or a GET prompted by another panel's broadcast, so a slow older answer never overwrites a newer state. While a change of this panel is on its way, revisions heard from other windows (a broadcast, a GET on focus) are kept but not applied; if the answer to the change is older than one of them, it is not shown as the result, the panel asks the companion, and when that cannot settle it the box is shown as uncertain rather than as "Removed from history.". A server error (5xx) after a click is treated like a lost answer: the panel asks the companion and announces what it says, and never just puts the box back. An answer to such a question that was asked before a later click in this panel is dropped too, and one that carries a newer clear generation (Clear history on another machine) resets the panel like a cleared one: summary, box and thread go, and it says so. Reopening the panel shows the state the companion reports. The request carries the panel's clear generation; a refusal as stale resets the panel like any other stale refusal.

Clear history is no longer in the panel. It is on the Settings page, under History, behind a confirmation ("Clear history now?" with "Yes, clear history" and Cancel; Escape cancels). Confirming does what the panel button used to: `POST /clear`, every per-window slot dropped from storage, and the new generation written as `clearGen`, so every open panel forgets its summary and question thread ("History was cleared in another window or on the Options page."). The history log file is kept. If the companion cleared but this browser's storage cleanup failed, the page says so ("History cleared. Could not reset this browser's panel state: ...") instead of claiming nothing was cleared; "Not cleared" is only for a refusal or an unreachable companion.

### The four modes and the pin

Choosing a mode button on a fresh panel with no source yet only keeps the choice (the pressed look moves and the mode is stored, so a right-click or the pin uses it); a mode is submitted when there is a source. Five large square buttons, left to right: Claude Dive, Claude Dip, the pin ("Summarize this page"), Codex Dip, Codex Dive. The four modes are black squares with a logo (see "Layout" above): full strength for Dive, washed out for Dip; each logo stands out from the black by at least 3:1 (2.5:1 for the darker Dip) (checked from the image files in `test/savehist.test.mjs`). The pressed mode looks physically pressed in (shifted down, no ledge, inset shading, a rim and glow in the provider's colour); there are no radio buttons. The mode buttons are created from one ordered list (`MODES` in `lib/modes.js`) with the pin appended between the two pairs, and nothing reorders them, so the Tab order is the same left to right. The Temp chat mode (a source copied to the clipboard for a ChatGPT temporary chat) was removed, with its clipboard permission, its button, its notes and its tests. A stored last-used mode of `temp` (an old install) is treated as no choice: the default mode (Codex Dip) is used, the stored key is removed on the next panel start, and a slot an old install left behind in the `temp` mode is not resumed or resubmitted (the panel shows the page and asks for a mode). The companion's `source` job mode is untouched; the extension no longer sends it.

### The pin button (Summarize this page)

The center button is a black square the size of the mode buttons with a white, solid map pin (a round head tapering to a sharp point, with a small round hole; inline SVG, `PIN_ICON` in `panel.js`), accessible name and tooltip "Summarize this page". It is an action, not a mode: it has no `aria-pressed`, never takes the pressed look (only a rim on hover and while held), and changes no setting (the stored mode and the pressed mode button stay as they were).

A click summarizes the page in the active tab of the panel's own window with the mode that is selected in this panel, as if the person had right-clicked the page and chosen Dip'n'Dive: the address goes through the same check as a right-click (`pickUrl` with the tab's address as the page address: http and https only), becomes the same per-window slot the menu writes (`makeSlot` in `lib/background-core.js`: `url`, a fresh `requestId`, `windowId`, `ts`, `consumed: false`, here with the panel's mode as `pendingMode`, as for a typed link), and is submitted by the same code, so the companion's own normalization (video ids, redirects), the clear generation, the history entry and the save box apply unchanged. The permission request is the first await, because Chrome only shows its prompt for a call made inside the click. That prompt can stay open for a long time, so each click carries an operation token: a newer pin click, any newer submission or mode-driven rerun, and any change of the clear generation (another window's Clear history, this panel's own, a stale refusal) make it stale, and a stale pin is dropped after every await without touching the panel or sending anything. The pin's messages have a line of their own under the buttons (`#pinmsg`) and never touch the busy flag, the status line or the error line of a job that is already running. If the permission is refused, the panel says "To summarize the open page, Dip'n'Dive needs to read its address. Click the pin again and choose Allow, or paste a link above." and nothing is sent; if the active tab is not an http or https page (chrome://, the new tab page, about:blank, a file, an extension page) it says "This page cannot be summarized. Open a web page (an http or https address) and try again."; with no tab, "No page is open in this window."; if the companion is not set up, the same line as the link field.

Permission, least privilege. A side panel can ask which tab is active, but Chrome returns that tab without its `url` unless the extension holds a permission that covers it (checked in a real Chrome 154 side panel by `tests/chrome/panel-pin.mjs`: `chrome.tabs.query` gives a tab with no `url`), and a click inside a side panel does not grant `activeTab` (that grant comes from the toolbar icon, the context menu or a keyboard shortcut). The options, smallest first:

1. An optional host permission for `https://*.youtube.com/*`: narrowest, and enough for the usual case (a video already playing). Rejected as the whole answer because the panel cannot tell that the active tab is YouTube without reading its address, and every other page would need a second grant anyway; the pin would then work for one site only, while the request is to summarize the page in the active tab.
2. An optional `tabs` permission, asked for by the first click on the pin: chosen. It lets the extension read the address and title of tabs through the API and nothing else: no page content, no scripts, no content scripts, no host access (the manifest still has none, and the extension still injects nothing). It is declared as `optional_permissions`, so nothing is held at install, adding it in this version did not disable existing installs (a new required permission would have), Chrome shows its one-time prompt only when the person clicks the pin, the person can take it back on the extension's card at `chrome://extensions`, and the next click then asks again. The code reads one thing only: the active tab of the panel's own window, and the address it hands on is the one a right-click would have used, sent to the person's own companion.
3. An optional all-sites host permission (`<all_urls>`): also readable addresses, but it lets the extension read and change every page's data. Rejected.
4. A required `tabs` permission: always on, shown at install and re-prompting installed copies. Rejected.

`chrome.permissions.request` is called first thing in the click handler, every time: when the permission is already held Chrome answers true at once without a prompt (3 ms in the real-Chrome check), so there is no `contains` call whose await could cost the click its user gesture. Real-Chrome verification (`node tests/chrome/panel-pin.mjs`, a real side panel and real tabs in a throwaway Chrome 154 profile, the harness companion with fake models): with the shipped manifest, the active web tab has no `url`, and a real click on the pin makes the panel call `chrome.permissions.request({ permissions: ["tabs"] })`, which Chrome leaves waiting for its native prompt (a script cannot click it) while nothing is sent and no slot is written; with a copy of the extension that holds `tabs` (what Allow does) and host access only for `localhost`, while the page tab is on `127.0.0.1` (so the address is visible through `tabs` and not through host access), the click reads the real tab, writes the window's slot with that address, and the companion summarizes that page with the selected mode, the summary and the save box appear, the history log has the entry, the stored mode and pressed button are unchanged, `chrome://version` and `about:blank` give the short message with nothing submitted, and back on the web page it works again. The one step no script can make is the click on Allow in Chrome's own prompt; the refusal path is covered by `test/pin.test.mjs` and the plain-page check in `tests/chrome/panel-plain.mjs` (`?perm=denied`).

### Question box and microphone (mouse only)

Below the result the panel has a box ("Ask a question"), a mic button and an Ask button. These controls are docked at the bottom of the panel: everything else (summary, thread, status) scrolls above them, and every message line (listening, errors, Enable microphone) grows upward from them, so nothing arriving while the person talks can move the mic button between the click that starts a recording and the click that stops it. Typing and Enter, or the Ask button, send the question. The mic is click to start, click again to stop: the button turns red and says Stop, the words appear in the box as they are recognized, and the second click sends the text automatically. Everything is reachable with the mouse. The previous questions and answers in this panel for this source (newest 6 turns, 8000 characters) and the Dip or Dive text on screen (first 4000 characters) go along with each question, so follow-ups work ("and why?", "tell me more about the second one"). Each earlier turn is sent in its own `<turn>` block and the summary in `<summary>`; they and the source are data, never instructions. The thread is forgotten when the source changes (another link, typed or right-clicked; the same video written another way keeps it), on Clear history (on the Settings page: every panel learns of it through a `clearGen` storage key and also from the generation number in the companion's answers). Clear history on another machine cannot reach this browser's storage, so every `POST /jobs` (summary and question) carries the clear generation the panel knows (`clearGeneration`, left out until the panel has heard one). If the companion answers 409 `stale_clear_generation`, the panel forgets its thread and summary, adopts the companion's generation, shows "History was cleared on another machine." (in the page for a button press, next to the question box for a question, which goes back into the box), and sends nothing again by itself: the next press or Ask is the person's own and carries the new generation. A link from a right-click or Go that was refused is dropped from storage so reopening the panel does not submit it later, and when the panel closes. The provider follows the pressed button: Claude Dive and Dip ask Claude, Codex Dip and Dive ask Codex (Claude when `/health` says Codex is unavailable).

Speech recognition is Chrome's built-in `webkitSpeechRecognition` (English, interim results, continuous mode), running in the side panel page itself. Chrome ends a continuous session by itself after about 15 seconds of silence (8 seconds if nothing is said at the start); when that happens, or when the panel is hidden, the recognized words are kept in the box and are not sent, with one line saying so, so a long pause never sends half a question. Words typed in the box before the mic is clicked stay, and the spoken words are added after them; Chrome sends the audio to Google's speech service. A side panel cannot show Chrome's microphone prompt, so the panel checks `navigator.permissions` for the microphone and, when it is not granted, shows an Enable microphone button. That opens `mic.html` in a normal tab, which calls `getUserMedia({audio:true})`, stops the tracks and tells the user to go back to the panel (the button to click in Chrome's prompt is "Allow while visiting the site", not "Allow this time"). If the computer itself blocks the microphone for Chrome (macOS Privacy and Security, Windows privacy switches), both the tab and the panel say so and name the setting instead of looping through the prompt. No offscreen document and no extra manifest permission are needed (evidence in RESULTS section 13).
